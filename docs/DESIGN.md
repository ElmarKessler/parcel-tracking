# Parcel Tracking API: Design

Status: Implemented · Author: Elmar Kessler · October 2026

## 1. Context

Small backend that tracks parcels from warehouse pick to delivery and computes pick routes through a warehouse grid. Built to learn C#/.NET (ASP.NET Core Minimal API, EF Core, xUnit) with production habits: an explicit state machine, idempotent event ingestion, tests, CI.

## 2. Goals and non-goals

**Goals**
- Create and read orders and parcels over REST.
- Parcel status changes only through events. Invalid transitions are rejected.
- Event ingestion is idempotent: the same event delivered twice changes state once.
- Pick route through a warehouse grid: shortest path between stops (BFS), stop order by nearest neighbour.
- Core logic unit-tested. CI runs build and tests on every push.

**Non-goals**
- Authentication, multi-tenancy, UI.
- Message broker, background workers, threads.
- Optimal route ordering (see 8).
- Cloud deployment (stretch only).

## 3. Architecture

One ASP.NET Core Minimal API project, SQLite through EF Core.

```
src/ParcelTracking.Api/
  Domain/      Order, Parcel, ParcelStatus, ParcelEvent, ParcelStateMachine
  Data/        AppDbContext, SeedData
  Services/    ParcelEventService
  Routing/     WarehouseLayouts, PickRoutePlanner
  Endpoints/   OrderEndpoints, ParcelEndpoints, ParcelEventEndpoints, WarehouseEndpoints, ApiErrors
  Program.cs
tests/ParcelTracking.Tests/
.github/workflows/ci.yml
```

Rules:
- `Domain/` and `Routing/` depend on neither ASP.NET nor EF Core. Pure code, unit-testable without a database.
- Endpoints stay thin: validate input, call a service, map the result to an HTTP status.
- Event handling lives in `ParcelEventService` and returns a result type, not an HTTP response. The idempotency logic is tested without HTTP.

## 4. Domain model

| Entity | Fields | Notes |
|---|---|---|
| Warehouse | Id, Name | Grid layout lives in code (`WarehouseLayouts`), keyed by warehouse Id. Not stored in the DB. |
| Order | Id, CustomerName, CreatedAtUtc, Parcels | |
| Parcel | Id, OrderId, WarehouseId, TrackingNumber, BinCode, Status | TrackingNumber generated by the server, unique. BinCode = bin letter in the warehouse grid. |
| ParcelEvent | Id, EventId, ParcelId, NewStatus, OccurredAtUtc, ReceivedAtUtc | EventId unique, supplied by the sender. |

Timestamps are `DateTime` in UTC. The EF Core SQLite provider has limited support for `DateTimeOffset` in comparisons and ordering.

## 5. Status state machine

```
Created -> Picked -> Packed -> Shipped -> Delivered
```

- Allowed: exactly one step forward.
- Rejected: skipping a step, going backwards, setting the same status again, any change after Delivered.
- Implemented as an explicit set of allowed (from, to) pairs in `ParcelStateMachine`, not as `to == from + 1` on enum values. Adding a status later (e.g. Cancelled from Created or Picked) means adding pairs to the set, not changing arithmetic that depends on enum order.

## 6. API

| Method | Path | Success | Errors |
|---|---|---|---|
| POST | /orders | 201 + Location | 400 |
| GET | /orders/{id} | 200 (order with parcels) | 404 |
| POST | /orders/{id}/parcels | 201 + Location | 400, 404 (order) |
| GET | /parcels/{id} | 200 | 404 |
| GET | /parcels/{id}/history | 200 (events, oldest first) | 404 |
| POST | /parcels/{id}/events | 201 new event, 200 duplicate | 400, 404, 409 |
| GET | /warehouses/{id}/pick-route?parcelIds=1,2,3 | 200 | 400, 404, 422 |

Event body: `{ "eventId": "...", "newStatus": "Picked", "occurredAt": "2026-10-25T09:00:00Z" }`

All errors use ProblemDetails (RFC 9457) via `AddProblemDetails()`. Validation errors return `ValidationProblem` with field-level messages.

## 7. Idempotent event ingestion

Events can arrive more than once: the sender retries after a timeout without knowing whether the first request succeeded (at-least-once delivery). The sender's `eventId` is the deduplication key. A timestamp is not: two events can share one.

Flow in `ParcelEventService.ApplyAsync`:
1. Look up `eventId`.
   - Exists with the same parcel and status: duplicate. Return the current parcel state, change nothing (200).
   - Exists with a different parcel or status: the eventId was reused for another event (409).
2. Load the parcel (404 if missing).
3. Check the transition with the state machine (409 if invalid; nothing is stored).
4. Insert the `ParcelEvent` and update `Parcel.Status` in one `SaveChangesAsync` call. EF Core wraps it in one transaction: both changes are stored, or neither is (201).

Safety net: a unique index on `ParcelEvent.EventId`. The database rejects a second row with the same eventId even if the check in step 1 is bypassed. On that error the service treats the request as a duplicate.

Known limitation: out-of-order arrival. If Packed arrives before Picked, the strict machine returns 409 and the sender must retry later. Alternative for later: accept events, order by `OccurredAtUtc`, apply when the gap is filled.

## 8. Pick route

Grid characters: `.` free, `#` shelf or wall, `S` start (dock), `A`–`Z` bins (walkable). Movement in 4 directions, each step costs 1. Each parcel's `BinCode` names its bin.

Algorithm (`PickRoutePlanner`, static, pure):
1. From the current position, run BFS over the grid. One BFS gives the distance to every cell in O(R·C).
2. Go to the nearest unvisited stop. Ties break on the lower parcel Id, so output is deterministic.
3. Repeat until all stops are visited, then return to `S`.
4. Total for k stops: O(k·R·C).

Output: ordered parcel Ids, steps per leg, total steps. A bin that cannot be reached returns 422 with the affected parcel Ids. Several parcels in the same bin produce legs of 0 steps.

Why not optimal: the best visiting order is a travelling-salesman problem, which is NP-hard. Nearest neighbour is simple and fast but not guaranteed optimal. Options if it matters: 2-opt improvement, or exact dynamic programming (Held-Karp) for small k.

## 9. Persistence

- SQLite file `parceltracking.db`.
- Schema created with `EnsureCreated()` at startup; one warehouse seeded.
- Trade-off: `EnsureCreated()` cannot evolve an existing schema. Switch to EF Core migrations before the first schema change.
- Indexes: unique on `Parcel.TrackingNumber`, unique on `ParcelEvent.EventId`, non-unique on `ParcelEvent.ParcelId` (history lookup).

## 10. Testing

| Level | What | How |
|---|---|---|
| Unit | State machine: every from/to pair | xUnit `[Theory]` + `[InlineData]` |
| Unit | Pick route: path around a wall, unreachable bin, bin missing from grid, greedy order, two parcels in one bin, no stops | xUnit, small hand-written grids |
| Service | New event; same event twice (one row, one status change); eventId reused with other payload; invalid transition stores nothing | `ParcelEventService` against SQLite in-memory |

SQLite in-memory instead of the EF Core InMemory provider: the InMemory provider does not enforce unique indexes or transactions, so it cannot test idempotency.

Optional: one end-to-end smoke test with `WebApplicationFactory`.
